# Atmosphere and Global Portal Artifact

## Observed root cause

`ImmersivePortalsBackend.createBoundary` creates two `DebugFlightPortal` instances as **global portals** and gives each a `60_000_000 x 60_000_000` quad. The Overworld boundary uses `(1,0,0)` and `(0,0,1)` as its axes, so it is a horizontal plane at the configured transition Y (the space boundary is the reverse direction). `PortalAPI.addGlobalPortal` deliberately makes the portal available to the client independently of normal entity/chunk tracking.

The pinned IP source establishes the precise cause: [`ViewAreaRenderer.generateTriangleForGlobalPortal`](https://github.com/iPortalTeam/ImmersivePortalsModForForge/blob/f60c277f8971d64a580faa5a110e410742b489e9/imm_ptl_core/src/main/java/qouteall/imm_ptl/core/render/ViewAreaRenderer.java) does **not** draw that full 60-million-block quad. It computes `r = effectiveRenderDistance * 16 - 16`, then, when camera-plane distance exceeds 200, applies `r *= 200 / distance`. It emits four camera-centered, portal-clamped corners at `+/-r`. At 12 chunks the rendered square is only 352 blocks across near the plane, and smaller farther away. Thus a square window is expected already 100 blocks below a Y=512 boundary. This is a render-distance-bounded mask, not the far edges of the enormous portal or missing target chunks. Increasing portal size cannot fix it; moving the boundary higher makes the window smaller/delays encounter without removing the cause.

The current `AltitudeVisuals` implementation reinforces this split: its `AFTER_SKY` stage and `ViewportEvent` callbacks run for the active renderer/pass, while the IP destination pass is a separate `LevelRenderer`. The same atmosphere calculation must be applied in every relevant pass if the destination world is rendered at all. A shader or fog adjustment applied only to the main Overworld pass cannot cover pixels produced by the portal pass.

## Compatible API/code points

* Crossing authority is in `DebugFlightPortal.canTeleportEntity`; do not remove the portal or make it non-teleportable. `FlightTransferCoordinator.canCross` and `FlightNetwork.clientCanCross` remain the readiness gates.
* Portal lifecycle is `PortalAPI.addGlobalPortal`, `GlobalPortalStorage.get(level).removePortals`, and `Portal.updateCache`. The tag `rocketmod:debug_elytra_boundary` is the stable ownership key.
* Destination preparation/readiness already observes `ClientWorldLoader.worldRendererMap` and `IEWorldRenderer.ip_getBuiltChunkStorage()` in `ClientFlightState`; this is the correct place to distinguish a loaded destination pass from an atmosphere-only frame.
* `AltitudeVisuals.Viewport` (`ComputeFogColor` and `RenderFog`) and `AltitudeVisuals.WorldRender.planet` (`RenderLevelStageEvent.AFTER_SKY`) are the project-owned visual hooks. They use `ClientFlightState.altitude(...)` and `virtualAltitude(...)`, so the authoritative transition height is already available without deriving it from the portal geometry.
* Verified in the [pinned `Portal.java`](https://github.com/iPortalTeam/ImmersivePortalsModForForge/blob/f60c277f8971d64a580faa5a110e410742b489e9/imm_ptl_core/src/main/java/qouteall/imm_ptl/core/portal/Portal.java): public `setIsVisible(boolean)` controls a protected `visible` flag serialized as `isVisible`. Its contract explicitly retains collision, teleportation and chunk loading. Vanilla `Entity.setInvisible` does not control portal rendering. Public `fuseView` (serialized) suppresses destination sky and preserves outer-world depth. `PortalLike.isFuseView()` is the renderer-facing accessor.

## Smallest robust fix (proposed)

1. Keep the two global portals and their `canTeleportEntity` checks for genuine IP crossing. Do not use a portal quad as the atmosphere mask.
2. Add an explicit client-side `atmosphereForPass(LevelRenderer/ClientLevel, camera)` helper and call it from the main pass and the IP destination pass. It should use the server-synced transition altitude, dimension direction, and camera Y, then apply the same sky darkening/fog in each pass.
3. Prefer `portal.fuseView = true` for the debug boundaries: this is the existing supported IP sky-suppression/depth-preservation mechanism and retains destination render passes for the readiness contract. Apply it before adding/syncing the global portal. Ensure the custom project sky/planet `AFTER_SKY` handler also skips its destination sky overlay under `PortalRendering.isRendering()` and `PortalRendering.getRenderingPortal().isFuseView()`; IP skipping vanilla sky alone does not automatically skip arbitrary Forge stage handlers.
4. In the main pass, render the dark atmosphere after native sky and before orbital terrain. In the fused destination pass, retain the parent sky rather than drawing another alpha-blended sky shell; keep fog consistent using the same physical altitude. Otherwise the shared alpha overlay would be composited twice inside the portal square. Also keep custom orbital terrain out of fused passes if it is a main-view backdrop, so it does not reintroduce a rectangular duplicate.

An alternative is the verified `portal.setIsVisible(false)` API and a main-pass atmosphere. It preserves IP teleportation and chunk loading, but **breaks the current readiness handshake**: `ClientFlightState.checkReadiness` requires `targetFrameTick` from an actual target renderer `AFTER_LEVEL` within 20 ticks. An invisible portal produces no destination pass, so Ready never arrives unless a separate bounded warmup rendering mechanism is added. Do not remove this readiness condition merely to make invisible portals cross. `fuseView` is the smaller implementation because it preserves the pass.

## Boundary height and verification

Moving the boundary from the current value to Y=1000--2000 reduces the chance that the quad edge enters the camera frustum during ordinary flight, but it is not a correctness fix. Validate at several altitudes and look directions (including horizon and straight down), with IP render distance/chunk loading varied. Acceptance requires: no four-edged sky window in either renderer pass; continuous darkening from the authoritative height; destination chunks still become Ready; and crossing still occurs only when both client and server readiness gates are true.

This conclusion and the API names are verified against the fixed Forge 1.20.1 IP source commit in docs/02. A client frame capture with the shipped `immersive-portals-3.0.7-all.jar` is still required to verify the resulting visuals and readiness; no runtime success is claimed here.
